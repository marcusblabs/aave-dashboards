Method & caveats

What this is for. A Balancer boosted pool holds the ERC-4626 wrapper, not the raw token, so the only question that matters here is whether a wrapper exists and how much room is left to deposit into it. That is the deposit cap. The same on-chain struct carries a borrow cap and it is deliberately not shown — it says nothing about wrapping capacity.
What is read. For each wrapper the page calls getSpokeConfig(assetId, spoke) on its hub for the deposit cap and the active/halted flags, plus totalAssets(), maxDeposit(address) and convertToAssets() on the wrapper itself — the last giving the ×rate beside each symbol, the assets-per-share a boosted pool would price against. All eth_call at latest over public RPC, in your browser, batched — no backend, no API key.
Every hub, not just Core. Aave v4 runs five hubs: Core, Prime, Plus and Global Dollar on Ethereum, and Core on Avalanche. Their wrappers are named per hub — waCore*, waPrime*, waPlus*, waPaxos*, waGlobalDollar* — so nothing here keys off the prefix.
Nothing is embedded but the five hub addresses. Each hub describes itself: getAssetCount(), then getSpokeCount and getSpokeAddress per asset, keeping the one spoke that answers symbol() — the wrapper. A token listed tomorrow appears by itself, with its own decimals and asset id.
Listed is not the same as wrappable. An asset can be live as collateral on a hub with no wrapper deployed against it — syrupUSDG on Global Dollar is exactly that case today. Those are listed under each hub and counted in the Awaiting a wrapper tile rather than quietly dropped, because they cannot go into a boosted pool until the wrapper ships.
Aave saying yes is only half of it. A Balancer v3 boosted pool routes through an ERC-4626 buffer held by the Balancer Vault, and that buffer has to be initialised for a given wrapper before any pool can use it. That is a Balancer-side step which nothing on Aave can report, so the page reads it straight from the v3 Vault at 0xbA1333…9ba9 — isERC4626BufferInitialized for the flag and getBufferBalance for the depth behind it. Each row is badged buffer live or no buffer, and the Pool-ready now tile counts only wrappers where both sides are true. A Vault read that fails shows buffer ? rather than being reported as absent.
How to read it. Caps are governance-set per hub and per spoke. Available is the room left before the cap, as the wrapper itself reports it. Bands: open under 40% filled, filling 40–90%, at cap above 90%. A cap of 2^40−1 shows as uncapped; a cap of 0 means the wrapper is deployed but closed to deposits.
Units. Figures are in native token units, not dollars — stablecoins are ≈ $1, but AVAX, BTC and ETH are not, so the headroom tile sums only the $-pegged wrappers. A token matching neither the dollar nor the non-dollar list is named in the status bar and left out of that total rather than guessed at. Click any address to copy it.
